## 一句话总结

> ⭐ "M3.1 Flash 把 Agent 成本打下来 70%" —— ⭐ **牌价没错，但结论要打两个折扣**。⭐ 第一，⭐ **"缓存贵 5 倍"是纯缓存对比**，⭐ 真实混合负载下只有 **1.1–1.7 倍**，⭐ 而且撞上 DeepSeek 高峰时段 MiniMax 反而**便宜 15%–46%**。⭐ 第二，也是本文最关键的：⭐ **如果你是 M Plan 订阅用户，整篇按 token 计价的算法对你不适用** —— ⭐ 你付的是订阅费，⭐ 消耗的是**额度窗口**，⭐ **缓存单价差 5 倍这件事，在订阅制下根本不会出现在你的账单上**。

## 〇、先说结论适用性：这篇文章对谁有用

这篇的核心分析基于**按量计费**（per-token pricing）。但很多人用的是**订阅制**。

**如果你在用 M Plan 这类订阅套餐，本文第 1–4 节的按 token 算账部分对你不适用。** 我自己就是 M Plan 用户，所以下面会专门有一节讲订阅制下该怎么看。

## 一、牌价核对：文章的数字都对

原始说法（阿鑫讲ai，2026-10-27）：

> MiniMax M3.1 Flash 的官方口径很漂亮：输入 1 元/百万 Token，输出 4 元/百万 Token，缓存读取 0.1 元/百万 Token，Agent 任务综合成本较前代降低 70%。

我把两家官方定价表都拉下来了（DeepSeek 按 1 USD = 6.68 换算）：

| 模型 | 缓存命中 | 缓存未命中 | 输出 |
|---|---|---|---|
| **MiniMax-M3.1-Flash** | 0.10 元 | 1.00 元 | 4.00 元 |
| **DeepSeek-V4.1-Flash** 闲时 | **0.020 元** | 1.002 元 | 4.008 元 |
| **DeepSeek-V4.1-Flash** 高峰 | 0.040 元 | 2.004 元 | 8.016 元 |

（DeepSeek 官方标美元：$0.003 / $0.15 / $0.60。闲时 = 高峰价一半，
**高峰时段 = 周一至周五 UTC 01:00–04:00 与 06:00–10:00**，即**北京时间工作日 09:00–12:00、14:00–18:00**。）

**逐条验证文章的说法**：

| 文章主张 | 核验 | 结论 |
|---|---|---|
| 输入 1 元、输出 4 元，与 DeepSeek 一样 | DS 闲时 1.002 元 / 高峰 2.004 元 | ✅ 闲时基本相同 |
| 缓存 0.1 元 vs 0.02 元，**差 5 倍** | 0.10 ÷ 0.020 = **5.0** | ✅ 精确 |
| "降 70%" 的参照系是 M3 而非 DeepSeek | M3 ≤512k：4.20/16.80/0.84；M3.1-Flash：1.00/4.00/0.10 | ✅ 倍数对得上 |

**所以文章的原始数字全部准确。** 问题出在它从数字推出的结论。

## 二、"缓存贵 5 倍"在真实负载下不成立

文章把"DeepSeek 缓存是 MiniMax 的 1/5"直接当作结论。但这**只在纯缓存命中的输入上成立**——真实 Agent 负载里，未命中输入和输出两边同价，把差距稀释了。

我按不同负载建模（输入 100K + 输出 5K 的一次调用）：

| 缓存命中率 | MiniMax | DS 闲时 | 倍数 | DS 高峰 | 倍数 |
|---|---|---|---|---|---|
| 0% | 0.1200 元 | 0.1202 元 | 1.00x | 0.2405 元 | **0.50x** |
| 50% | 0.0750 元 | 0.0711 元 | 1.05x | 0.1423 元 | **0.53x** |
| 80% | 0.0480 元 | 0.0417 元 | 1.15x | 0.0834 元 | **0.58x** |
| 90% | 0.0390 元 | 0.0319 元 | 1.22x | 0.0637 元 | **0.61x** |
| 95% | 0.0345 元 | 0.0270 元 | 1.28x | 0.0539 元 | **0.64x** |
| 99% | 0.0309 元 | 0.0230 元 | 1.34x | 0.0461 元 | **0.67x** |

**换几种负载结构（命中率 95%）：**

| 负载 | MiniMax | DS 闲时 | 倍数 | DS 高峰 | 倍数 |
|---|---|---|---|---|---|
| 100K 输入 / 1K 输出 | 0.0185 元 | 0.0109 元 | 1.69x | 0.0218 元 | **0.85x** |
| 100K / 5K（典型 Agent） | 0.0345 元 | 0.0270 元 | **1.28x** | 0.0539 元 | **0.64x** |
| 10K / 2K（短问答） | 0.0095 元 | 0.0087 元 | **1.09x** | 0.0174 元 | **0.54x** |
| 200K / 20K（重生成） | 0.1090 元 | 0.0940 元 | 1.16x | 0.1880 元 | **0.58x** |

### 三个结论

**① 差距从没到过 5 倍。** 最高 1.69x，多数落在 1.1–1.3x。5 倍是**纯缓存项**的对比，不是账单对比。

**② 撞上 DeepSeek 高峰时段，MiniMax 反而更便宜。** 高峰时 DeepSeek 输出价翻倍（$0.60→$1.20），MiniMax 输出价固定 4 元不变。而**北京时间工作日 09:00–12:00、14:00–18:00 正是 DeepSeek 高峰**——这恰好覆盖大部分 Agent 活跃时段。

**③ 输出占比越高，MiniMax 越吃亏。** 输出单价两边相同（4 元 vs 4.008 元），所以**输出越多，缓存那点小优势越被稀释**。短问答场景 MiniMax 优势只有 1.09x，高峰时甚至只有 0.54x（DeepSeek 更便宜一倍）。

## 三、真正决定账单的是返工，不是单价

文章这部分说得很好，而且引用的两个数据比价目表重要得多：

**① 同一任务重复运行，token 消耗可达 30 倍。**

**② Artificial Analysis 的独立测算**：M3.1 Flash 在 Intelligence Index 上平均 **$0.22/任务**，M3 是 **$0.51**，降幅 **57%**，比官方宣称的 70% 低 13 个百分点。

**③ 腾讯云架构评审那句话最该记住**：

> 降价七成是调用价，不是你的任务账单。

**"牌价降幅"和"任务成本降幅"之间的距离，隔着三样东西**：

| 因素 | 影响机制 |
|---|---|
| **任务成功率** | 同一个任务跑 1 次 vs 跑 5 次才成功 → 成本差 5 倍 |
| **重试率** | 工具调用失败、超时、限流后的重试 |
| **人工接管率** | 模型搞不定、转人工的部分 → 不只是 token 成本，还有你的时间 |

**一个便宜 70% 但需要重试 3 次的模型，比贵 20% 但一次过的模型更贵。**

|---|---|---|

**跨 SaaS 自动化工作流 MiniMax 反超，软件工程 DeepSeek 领先 3.3 分。**

选型要点：
- **工具编排 / 跨系统自动化** → M3.1 Flash
- **代码 / 软件工程** → DeepSeek

- **高频短问答** → 两者几乎打平，DS 高峰期反而更优

## 五、⭐ 如果你用的是 M Plan：整篇按 token 算账对你不适用

**这是我写这篇时最想说的。**

我自己的 OpenClaw 配置是：

```json
"minimax-portal": {
  "baseUrl": "https://api.minimaxi.com/anthropic",
  "api": "anthropic-messages",
  "apiKey": "<订阅 Key>",
  "models": ["MiniMax-M3", "MiniMax-M3.1-Flash"]
}
```

**订阅 Key**——不是按量计费的 API Key。这两者在 M Plan 文档里是明确分开的：

> 改用按量计费：需要使用套餐覆盖范围之外的资源，或用于生产环境时，可使用普通按量计费 API Key，费用从开放平台账户余额中扣除。**它与订阅 Key 相互独立，不能混用。**

### 订阅制的成本模型完全不同

| | 按量计费 | M Plan 订阅 |
|---|---|---|
| 付什么 | 每次调用的 token 费 | 固定月费 |
| 成本函数 | token 数 × 单价 | **是否超过额度窗口** |
| 缓存单价差 5 倍 | **直接影响账单** | **完全不影响** |
| 边际成本 | 线性增长 | 窗口内为 0 |
| 该优化什么 | 减少 token | **减少额度消耗 + 减少返工** |

**在 M Plan 下，"缓存贵 5 倍"这件事根本不会出现在你的账单上。** 你消耗的是额度窗口，而额度消耗的计量维度是**模型、上下文长度、任务复杂度、思考深度**——跟缓存单价无关。

### M Plan 的额度机制

**三个档位**（额度相对 Go 档）：

| 档位 | 用量 | 定位 |
|---|---|---|
| Go | 1x（基准） | 入门，简单调研 / 轻量写作 / 小范围代码修改 |
| Explore | 3x | 日常主力，日常辅助编程、长任务 |
| Build | 12x | 高频使用，长上下文、复杂编程、大量多模态 |

**两个独立的额度窗口**：

| | 5 小时窗口 | 周窗口 |
|---|---|---|
| 适用 | 非视频模型（文本/图像/音频） | **所有模型**（含视频） |
| 周期 | 5 小时 | 7 天 |
| 刷新 | 到点恢复上限，**未用完不累积、不结转** | 同左 |

> 两个窗口都从**第一次使用**开始计时。比如 10:00 首次使用，5 小时窗口就在 15:00 结束——**即使 12:00 就用完了，也得等到 15:00 才恢复**。

**这跟按量计费有个关键差别**：按量计费是**用多少付多少**，订阅制是**窗口内随便用、超了要等**。所以订阅制下真正要优化的是：

1. **别撞窗口上限** —— 撞了就得等 5 小时
2. **别在窗口末尾启动长任务** —— 5 小时窗口从首次使用起算，不是从你开始跑任务起算

### 订阅制下真正消耗额度的四个维度

M Plan FAQ 明确列了：

- **模型与模态**：视频生成消耗远高于文本
- **上下文长度**：对话越长、读的文件代码越多，每次请求处理得越多
- **任务复杂度**：多步骤 Agent 任务会连续发多次请求 + 调工具，**消耗明显高于单次问答**
- **思考深度**：思考深度越高，生成的思考内容越多，消耗越多

> ⚠️ **`MiniMax-M3.1-Flash` 始终开启思考，无法关闭**，运行时不要用 `/think off`。

**第三条对 Agent 场景特别重要**——这也是为什么"返工"在订阅制下同样是成本主线：多步骤 Agent 任务消耗明显更高，重试就是重复消耗。

### 怎么查自己的额度

三种方式：

```bash
# ① MiniMax CLI（最方便）
mmx quota

# ② API
curl --location 'https://www.minimax.cn/v1/token_plan/remains' \
--header 'Authorization: Bearer <API Key>' \
--header 'Content-Type: application/json'

# ③ 网页控制台
# https://platform.minimax.cn/console/usage
```

> 我实测 ② 这个接口用订阅 Key 会返回 `status_code: 1004 / login fail`，
> 说明**订阅 Key 和按量 API Key 在这个接口上也是分开的**——或者需要用 `minimax.cn` 域名的按量 Key。
> 最可靠的还是 `mmx quota` 或网页控制台。

## 六、所以订阅制用户该怎么选型

**别再用"每百万 token 多少钱"来做决策。** 换成这三个问题：

### ① 你的额度窗口会用满吗？

如果你的负载**稳定低于额度**，那两家贵 5 倍还是 1.2 倍**毫无意义**——你根本没按量付费。

**真正的问题是：会不会撞窗口？** 如果会，用量大的模型就是"更早撞上限"的意思（因为它消耗额度更快，或者它更贵）。

M Plan FAQ 提到的限流叠加机制值得注意：

> 额度限制与请求速率限制分别计算。即使还有套餐额度，短时间内发送过多请求，或遇到高峰时段的动态限流，也可能暂时无法调用。

### ② 哪个返工少？

这在订阅制下**更关键**，因为返工消耗的是额度窗口。

对照基准：
- **DeepSWE v1.1**：DeepSeek 77.0 vs M3.1 Flash 73.7 → **代码任务 DeepSeek 少返工**
- **Automation-Bench v1.0.6**：M3.1 Flash 62.2 vs DeepSeek 60.5 → **跨系统自动化 M3.1 Flash 少返工**

**任务成功率直接换成额度消耗。** 一个多返工 10% 的模型，等于多消耗 10% 的窗口。

### ③ 你的任务类型分布如何？

| 你的主要负载 | 建议 |
|---|---|
| 跨 SaaS 编排 / 工具调用 | M3.1 Flash（Automation-Bench 反超 + 200+ TPS） |
| 代码 / 软件工程 | DeepSeek V4.1 Flash（DeepSWE 领先 3.3 分） |
| 长上下文低输出 | M3.1 Flash（输出少 → 思考少 → 额度消耗低） |
| 短问答高频 | 看额度够不够，两者差异不大 |

## 七、免费档的坑（顺手记一下）

文章提到 OpenCode 有个限时免费档 `minimax-m3.1-flash-free`，但有个硬限制：

> 这个免费档只认 OpenCode 客户端——你用 curl 或自己的程序直连它的推理接口，会返回 **403 FreeTierError**。

想在自有代码里免费用，得走 **OpenRouter 的 `:free` 版本**。Vercel AI Gateway 也提供过 `npx vercel ai-gateway setup`，然后在 Agent 里选 `minimax/minimax-m3.1-flash`。

**免费档的限流和功能限制，决定了它只能用来"感受一下"，不能拿来跑真实的长任务账单。**

## 八、给不同人的行动清单

### 如果你用按量计费

1. **算你自己的负载**——别用"缓存差 5 倍"这个结论，用你的实际缓存命中率 × 输入输出比
2. **非紧急任务排到深夜**——DeepSeek 闲时（北京时间 00:00–09:00 及周末）成本直接减半，比纠结选谁有效
3. **盯返工率**——那 30 倍的 token 消耗才是账单主线

### 如果你用订阅制（像我）

1. **忽略所有按 token 的比价**——你付的是订阅费
2. **定期 `mmx quota`**——知道离窗口上限还有多远，比知道单价有用
3. **把长任务安排在窗口早期**——5 小时窗口从首次使用起算，不是从任务起算
4. **用基准分数选型，不用价格选型**——返工率决定你多久撞一次上限
5. **降低思考深度**（如果模型支持）——M3.1 Flash 不行，但 M3 可以；思考内容直接吃额度
